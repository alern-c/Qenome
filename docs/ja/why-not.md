# なぜ他の方法ではないのか

ここに挙げる道具は、問いの一部にすでに答えています。Qenome はそれらを置き換えません。ローカルの行数は本番 D1 の請求ではなく、ここで行数が減っても請求が下がるとは限りません。カウンタの作り方と、本番と違い得る点は[精度と本番 D1](accuracy.md)にあります。

**EXPLAIN QUERY PLAN。** 計画は、SQLite がインデックスを使うつもりかをすでに示します。データのコピーに対して文を実行しないので、結果の行が変わったか、何行読み書きしたか、データベースファイルがどれだけ増えたかは出ません。Qenome は両方のサンドボックスコピーで文を実行し、その比較の横に計画を置きます。カウンタはローカル D1 と同じ数え方（workerd のパッチ）を、Qenome 自身のビルドで使います。ローカル D1 のエンジンとは結果が違うことがあります。

**`wrangler dev`。** `wrangler dev` で動く Worker は、D1 の結果 `meta` に `rows_read` と `rows_written` をすでに返します。対象は [`run` と `all`](https://developers.cloudflare.com/d1/worker-api/prepared-statements/)（エイリアスとして文書化されています）と [`batch`](https://developers.cloudflare.com/d1/worker-api/return-object/) です。`raw`、`first`、`exec` にはこの `meta` がありません。これはローカル D1 エンジンでの1回の実行です。候補のインデックスをコピー上に作って、今のスキーマと比べることはしません。

**`wrangler d1 execute --local`。** `--json` を付けると、そのコマンドの結果 `meta` に `rows_read` と `rows_written` が入り、所要時間も出せます。時間は実行のたびに動きます。渡した SQL を実行するだけで、候補をサンドボックスのコピーに適用して組で判定することはしません。Qenome は元のデータベースを変えません。

**`wrangler d1 insights`。** 本番では、この experimental なコマンドが、クエリごとの `avgRowsRead`、`avgRowsWritten`、実行回数をすでに一覧にします。聞く期間のリモート分析を読みます。候補のインデックスは試さず、バインド値も記録しません。本番で実際に起きたことを見るために使ってください。Qenome はその数値を読まず、D1 がいくら請求するかは分かりません。手順の詳細は[本番と自分で照合する方法](accuracy.md#本番と自分で照合する方法)です。

**Qenome が足すもの。** 今のスキーマと候補1本を、サンドボックスのコピーで、同じ条件で繰り返し比べ、行数から判定を出します。判定は `improved`、`no-effect`、`needs-check`、そして `--migration` の変更では `regressed` です。時間は参考値です。計時した実行では A/A のノイズ幅を出し、その幅で判定も終了コードも変えません。`--runs 0` は計時を省き、判定は残します。`--scale` は同じ比較を、生成したデータで2つか3つのサイズについて繰り返します。その行は手元の生成データであり、本番 D1 の請求ではありません。`--migration` は、インデックスの削除を含むスキーマ変更をサンドボックスのコピーで調べます。`--format json` はエージェントと CI にレポートを渡し、終了コードが一致・不一致・比較不能を分けます。

**インデックスを入れてアプリを見る。** それは出荷するデータベースへインデックスを書き込みます。Qenome は先にサンドボックスのコピーで候補を試すので、ローカルの行数が減らない候補はマージの前に捨てられます。デプロイしたあとの本番の確認は `wrangler d1 insights` です。ローカルの行数が減ったことは、請求が下がった証明にはなりません。
