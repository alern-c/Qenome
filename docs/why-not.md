# Why not ...

These tools already answer part of the question. Qenome does not replace them. A local row count is not a production D1 bill, and a lower count here does not mean the bill will fall. How the counters are built, and what can differ from production, is in [Accuracy and production D1](accuracy.md).

**EXPLAIN QUERY PLAN.** The plan already says whether SQLite expects to use an index. It does not run the statement on a copy of the data, so it does not show whether the result rows changed, how many rows were read or written, or how much the database file grew. Qenome runs the statement on both sandbox copies and puts the plan next to that comparison. The counters use the same counting as local D1 (workerd patch), on Qenome's own build, which can differ from the local D1 engine.

**`wrangler dev`.** A Worker running under `wrangler dev` already returns `rows_read` and `rows_written` in the D1 result `meta` for [`run` and `all`](https://developers.cloudflare.com/d1/worker-api/prepared-statements/) (documented as aliases) and for [`batch`](https://developers.cloudflare.com/d1/worker-api/return-object/). `raw`, `first`, and `exec` do not include that `meta`. It is one execution on the local D1 engine. It does not build a candidate index on a copy and compare it with the current schema.

**`wrangler d1 execute --local`.** With `--json`, the result `meta` includes `rows_read` and `rows_written` for that command, and the command can also print a duration. The duration moves from run to run. The command runs the SQL you give it. It does not apply a candidate on a sandbox copy and judge the pair. Qenome leaves the original database unchanged.

**`wrangler d1 insights`.** On production, this experimental command already lists queries with `avgRowsRead`, `avgRowsWritten`, and how often they ran. It reads remote analytics for the period you ask for. It does not try a candidate index, and it does not record bind values. Use it for what production already did. Qenome does not read those metrics and cannot tell you what D1 will charge. [How to check against production yourself](accuracy.md#how-to-check-against-production-yourself) is the longer procedure.

**What Qenome adds.** One repeatable comparison of the current schema and one candidate, on sandbox copies, with a verdict from the row counts: `improved`, `no-effect`, `needs-check`, or `regressed` when `--migration` is the change. The times are a reference. When a run is timed, the report shows an A/A noise band and does not let that band change the verdict or the exit status. `--runs 0` skips the timing and keeps the verdict. `--scale` repeats the same comparison at two or three generated sizes. Those rows are generated data on this machine, not a production D1 bill. `--migration` checks a schema change on the sandbox copies, including one that drops an index. `--format json` gives the report to an agent or to CI, and the exit status separates a match, a mismatch, and an incomparable result.

**Applying the index and watching the app.** That writes the index into the database you ship. Qenome tries the candidate on a sandbox copy first, so you can drop one that does not lower the local counts before the merge. After it is deployed, `wrangler d1 insights` is the production check. A lower local count is not proof that the bill fell.
